# Задача: поручения документооборота через OData 1С

Техническое задание для разработчика / агента в проекте **RegAgent**.

---

## 1. Цель

Реализовать получение поручений (задач исполнителя) из **1С:Документооборот** через OData, извлечение ключевых полей по каждому поручению и **цветовую маркировку** по срочности и критичности (просрочка, «сегодня», ближайшая неделя, остальное).

Результат должен быть доступен в RegAgent (инструмент агента, API-слой или UI-виджет — по согласованию с текущей архитектурой проекта).

---

## 2. Контекст

### 2.1. Две публикации OData 1С

| Назначение | Базовый URL | Переменные окружения |
|------------|-------------|----------------------|
| ERP (erp_pm) | `http://192.168.2.229:81/erp_pm/odata/standard.odata` | `ODATA_BASE_URL` |
| Документооборот (/doc) | `http://192.168.2.229:81/doc/odata/standard.odata` | `DOCFLOW_ODATA_BASE_URL` (рекомендуется явно) |

**Важно:** поручения документооборота читаются из публикации **`/doc`**, а не из `erp_pm`. Если `DOCFLOW_ODATA_BASE_URL` не задан, URL можно вывести из `ODATA_BASE_URL`, заменив сегмент `/erp_pm/` на `/doc/` (логика уже реализована в Constructor backend: `Consturctor/backend/app/services/docflow_tasks.py` → `docflow_base_url()`).

### 2.2. Аутентификация

Использовать переменные из `RegAgent/.env` (пароли **не** хардкодить и **не** включать в документацию):

| Переменная | Назначение |
|------------|------------|
| `ODATA_USERNAME` | Логин OData (Basic Auth) |
| `ODATA_PASSWORD` | Пароль OData |
| `DOCFLOW_ODATA_USERNAME` | *(опционально)* отдельный логин для /doc |
| `DOCFLOW_ODATA_PASSWORD` | *(опционально)* отдельный пароль для /doc |

Fallback-цепочка (как в Constructor): `DOCFLOW_ODATA_*` → `ODATA_*` → `ERP_LOGIN` / `ERP_PASSWORD`.

HTTP: **Basic Auth**, заголовок `Accept: application/json`, таймаут — разумный (например 30 с).

### 2.3. Существующие артефакты RegAgent

- `data/odata_organization_keys.json` — GUID организаций (НП, АЛ, МГ и т.д.)
- `data/odata_department_keys.json` — GUID подразделений

Для фильтрации поручений по исполнителю используется справочник пользователей документооборота, а не эти файлы напрямую; ключи организаций/подразделений могут понадобиться при расширении фильтров.

### 2.4. Эталонная реализация

Портировать или переиспользовать логику из:

- `Consturctor/backend/app/services/docflow_tasks.py` — OData-запросы, маппинг полей, поиск пользователя
- `Consturctor/backend/app/services/erp_tasks.py` — `task_is_late()`, парсинг дат 1С
- Инструмент backend: `onec.docflow_tasks`

## 3. Источник данных

### 3.1. Основная сущность OData

В 1С:Документооборот поручения исполнителю представлены как **задачи**, а не отдельный документ `Document_*`:

| Сущность OData | Тип в 1С | Назначение |
|----------------|----------|------------|
| **`Task_ЗадачаИсполнителя`** | Задача исполнителя | **Основной источник поручений** |
| `Catalog_Пользователи` | Справочник пользователей | Поиск `Ref_Key` по ФИО исполнителя |
| `BusinessProcess_Задание` | Бизнес-процесс «Задание» | Связанная сущность (в allowlist Constructor; для карточки поручения — опционально) |

Отдельной сущности вида `Document_Поручение` в текущей кодовой базе **не обнаружено**. Перед реализацией рекомендуется проверить `$metadata` публикации `/doc`:

```http
GET {DOCFLOW_ODATA_BASE_URL}/$metadata
```

и каталог сущностей:

```http
GET {DOCFLOW_ODATA_BASE_URL}/
```

### 3.2. Пример запроса списка поручений

1. Найти GUID исполнителя:

```http
GET Catalog_Пользователи?$top=5&$filter=Description eq '{ФИО}'
```

2. Получить задачи исполнителя (только открытые — опционально):

```http
GET Task_ЗадачаИсполнителя
  ?$top=200
  &$orderby=Date desc
  &$filter=Исполнитель eq cast(guid'{user_key}','Catalog_Пользователи')
            and Executed eq false
```

Фильтры OData: экранировать одинарные кавычки в строках (`'` → `''`), даты — `datetime'YYYY-MM-DDTHH:MM:SS'`.

### 3.3. Идентификация текущего пользователя

ФИО исполнителя брать из сессии RegAgent (JWT / `REGAGENT_TEST_FIO` при тестовом входе), а не из аргументов без проверки.

## 4. Поля для извлечения по каждому поручению

Минимальный набор (маппинг уже описан в `docflow_tasks._map_task`):

| Поле OData (1С) | Поле результата | Описание |
|-----------------|-----------------|----------|
| `Ref_Key` | `id` | Уникальный ключ задачи |
| `Number` | `number` | Номер поручения |
| `Date` | `created_at` | Дата создания |
| `СрокИсполнения` | `due_at` | Срок исполнения |
| `ДатаИсполнения` | `completed_at` | Фактическая дата выполнения |
| `Executed` | `done` | Признак выполнения (`true` / `false`) |
| `Description` / `ПредметСтрокой` | `title` | Тема / предмет поручения |
| `Описание` / `РезультатВыполнения` | `comment` | Текст поручения или результат |
| `СостояниеБизнесПроцесса` | `approval` | Состояние согласования БП |
| *(из фильтра)* | `performer` | ФИО исполнителя |
| — | `status` | `открыта` / `выполнена` (из `Executed`) |
| — | `source` | Константа `"документооборот"` |
| — | `late` | Просрочено при выполнении (см. §5) |
| — | `urgency_tier` | Уровень срочности для раскраски (см. §5) |
| — | `color` | CSS/HEX-цвет или токен темы |

**Расширяемые поля** (если доступны в `$metadata` / `$expand`):

- `Автор` → ФИО автора поручения (`Catalog_Пользователи`)
- `Предмет` / ссылка на документ-основание
- `Важность`, `Приоритет` — если есть в конфигурации ДО
- `BusinessProcess` / `Задание` — связь с `BusinessProcess_Задание`

Пустые даты 1С (`0001-01-01…`) считать отсутствующими.

## 5. Правила раскраски по срочности / критичности

### 5.1. Уровни для **открытых** поручений (`Executed = false`)

Вычислять относительно **локальной даты** (без времени) на `due_at`. Если `due_at` отсутствует — уровень `none`.

| Уровень (`urgency_tier`) | Условие | Цвет (рекомендация) | Метка |
|--------------------------|---------|---------------------|-------|
| `overdue` | `due_at` < начало сегодня | `#DC2626` (красный) | Просрочено |
| `today` | `due_at` = сегодня | `#EA580C` (оранжевый) | Срок сегодня |
| `week` | `due_at` в интервале (завтра … +7 дней) | `#CA8A04` (жёлтый) | На этой неделе |
| `later` | `due_at` > +7 дней | `#16A34A` (зелёный) | Не срочно |
| `none` | срок не указан | `#6B7280` (серый) | Без срока |

**Приоритет:** если несколько условий формально пересекаются, брать **наиболее критичный** уровень: `overdue` > `today` > `week` > `later` > `none`.

### 5.2. **Выполненные** поручения (`Executed = true`)

| Уровень | Условие | Цвет |
|---------|---------|------|
| `done_late` | `completed_at` > `due_at` (обе даты заданы) | `#DC2626` или приглушённый красный |
| `done_ok` | выполнено в срок или без срока | `#6B7280` (серый) / `#16A34A` (зелёный) |

Флаг `late` в Constructor: `task_is_late(done=True, completed_at, due_at)` — только для **завершённых** задач.

### 5.3. Отображение

- Цвет — фон строки, бейдж срока или левая полоска (согласовать с `RegAgent/app/ui/theme.py`).
- В списке сортировка по умолчанию: сначала `overdue`, затем `today`, затем `week`, внутри уровня — по `due_at` ASC.
- Текстовая подпись уровня обязательна для доступности (не только цвет).

## 6. Критерии приёмки

1. **Подключение:** при корректных переменных из `.env` клиент успешно обращается к `{DOCFLOW_ODATA_BASE_URL}`; при 401/402 выдаётся понятная ошибка («учётка не добавлена в базу документооборота»).
2. **Данные:** для заданного ФИО возвращается список поручений из `Task_ЗадачаИсполнителя` с полями из §4.
3. **Фильтры:** поддерживаются `only_open` (по умолчанию `true`), опционально `date_from` / `date_to`, `limit` (макс. 200).
4. **Раскраска:** каждое открытое поручение получает `urgency_tier` и `color` согласно §5; просроченные открытые — красные.
5. **Без секретов:** пароли только из `.env`; в логах и UI пароли не выводятся.
6. **Повторяемость:** логика покрыта unit-тестами (маппинг, расчёт tier, парсинг дат 1С) по образцу `Consturctor/backend/tests/test_docflow_tasks.py`.
7. **Пустые состояния:** если пользователь не найден в `Catalog_Пользователи` — пустой список + предупреждение, без падения приложения.
8. **Документация:** в `RegAgent/.env.example` добавлены `DOCFLOW_ODATA_BASE_URL`, `DOCFLOW_ODATA_USERNAME`, `DOCFLOW_ODATA_PASSWORD` (опционально).

## 7. Шаги реализации (high level)

1. **Конфиг:** расширить `RegAgent/app/config.py` и `.env.example` — URL и учётные данные документооборота, таймаут OData.
2. **OData-клиент:** модуль `app/services/docflow_odata.py` (или порт `docflow_tasks.py`):
   - `docflow_base_url()`, `docflow_auth()`, `docflow_configured()`
   - HTTP GET с Basic Auth
   - `find_user_key(fio)`, `list_docflow_tasks(...)`
3. **Маппинг и срочность:** `_map_task()` + функция `urgency_tier(due_at, done, completed_at) → tier, color`.
4. **Инструмент агента:** зарегистрировать tool (например `onec.docflow_tasks` или `regagent.docflow_porucheniya`) в runtime RegAgent; вход: `fio` (опционально), `only_open`, `date_from`, `date_to`, `limit`.
5. **UI (опционально):** виджет списка поручений на workspace с цветовыми бейджами и сортировкой по §5.3.
6. **Тесты:** маппинг, tier-логика, формирование `$filter`, обработка ошибок 401/404.
7. **Проверка на стенде:** пользователь `ODATA_USERNAME` должен существовать в базе **документооборота** (не только ERP).

## 8. Риски и зависимости

| Риск | Описание | Митигация |
|------|----------|-----------|
| Разные учётки ERP и ДО | OData-пользователь может быть заведён только в erp_pm | Отдельные `DOCFLOW_ODATA_*` или заведение пользователя в /doc |
| Сеть / VPN | `192.168.2.229` доступен только из корпоративной сети | Проверка connectivity, понятные сообщения об ошибке |
| `$metadata` расходится с ожиданиями | Имена полей могут отличаться в версии конфигурации ДО | Discovery через `$metadata`; graceful fallback на известные поля |
| Даты 1С | Годы 3xxx / смещение +2000 | Использовать `from_1c_datetime()` из эталона |
| Нет срока | Много поручений без `СрокИсполнения` | Уровень `none`, серый цвет |
| Производительность | `$top=200` на человека | Пагинация `$skip` при необходимости; кэш на 1–5 мин |
| Права OData | Read-only; изменение поручений не входит в задачу | Только GET-запросы |
| RegAgent без OData-слоя | Сейчас в RegAgent есть COM-инструменты, OData — в `.env`, но не в коде | Новый модуль; не смешивать с COM без явной абстракции |

### Зависимости

- Доступность публикации OData `/doc` на сервере 1С
- Файл `RegAgent/.env` с заполненными `ODATA_*` (и при необходимости `DOCFLOW_*`)
- Для UI: PySide6 / существующая тема RegAgent
- Constructor backend (`:7812`) — **не обязателен** для прямого OData-чтения, но может использоваться как прокси через tool `onec.docflow_tasks`, если предпочтительнее единая точка интеграции
