# Серверные инструменты: ресурсы, вызовы, OCR

Файл описывает инструменты, которые исполняет backend Constructor, и отдельно распознавание сканов. Железо на 500 человек — в `спецификация-серверов.md`: сервер приложения с RTX 5090 32 ГБ как раз под расшифровку совещаний и распознавание сканов.

Цифры «сколько раз в день» — оценка по тому, как код вызывает инструмент, а не замер на проде. Жёсткие пределы (один прогон на видеокарте, размер файла, таймаут, кэш) взяты из кода.

## 500 сотрудников и параллельность

Одновременно работают не все 500. В рабочий час в программе обычно десятки человек, не сотни. Тяжёлые вызовы ещё реже: расшифровка нужна на запись совещания, OCR — на скан или фото. Письмо, задача 1С и карточка пользователя видеокарту не занимают.

Практическая картина на 500 человек:

| Нагрузка | Кто её создаёт | Что упирается |
|---|---|---|
| Расшифровка | протокол совещания, одно аудио на запуск | одна видеокарта, очередь из одного слота |
| OCR скана | вложение агента, регламент, зарплатные файлы | сейчас облачная модель; локальная модель села бы на ту же 5090 |
| Агенты (текст) | каждый запуск агента, много шагов | квота API Cursor, процесс Node на сервере |
| 1С, почта, календарь | почти каждый рабочий запуск | сеть и сами 1С / Exchange, не GPU |

Повтор одного и того же аудиофайла расшифровку не запускает: ответ берётся по хэшу файла. У OCR такого кэша нет: тот же скан, приложенный заново, распознаётся снова.

## Что ест ресурсы

По убыванию локальной нагрузки:

1. `audio.transcribe` — видеокарта, несколько больших моделей по очереди, минуты на запись.
2. OCR сканов и фото — либо облачное зрение (по умолчанию), либо локальная VLM на 14 млрд параметров.
3. Запуски агентов через Cursor SDK — частые, но считают в облаке. На сервере остаётся CPU и память процесса Node.
4. Чтение 1С, Exchange и скачивание вложений — частые, упираются в чужие серверы и сеть.
5. Остальной каталог (`users.*`, `notify.send`, `chat.send_direct`, чтение уже готовой расшифровки) — база и диск.

Эмбеддинги `BAAI/bge-m3` лежат в коде платформы агентов и в backend Constructor не подключены. На видеокарту совещаний их ставить не нужно.

## `audio.transcribe`

Расшифровка аудио-вложения запуска. Если задан `ASR_GPU_URL`, файл уходит на отдельный процесс `asr-server` (только localhost, CUDA). Если адрес пустой, работает запасной путь: `faster-whisper`, модель `small`, beam 5, на CPU. В комментарии к коду: около 8 минут на 25 минут аудио. Для 500 человек этот запасной путь годится на единичные записи, не на очередь совещаний.

GPU-цепочка, модели грузятся по одной и после шага выгружаются:

| Шаг | Модель | Зачем | Точность весов |
|---|---|---|---|
| Кто говорит | `nvidia/Nemotron-3-Diarization` | метки «Голос N», в том числе одновременно | bfloat16 |
| Наложение двух голосов | `speechbrain/sepformer-whamr16k` | развести одновременную речь кусками по 10 с | как в SpeechBrain |
| Отпечаток голоса | `speechbrain/spkrec-ecapa-voxceleb` | вектор, чтобы потом узнать человека | как в SpeechBrain |
| Текст | `openai/whisper-large-v3` | реплики с таймкодами | float16 |

Сервис берёт не больше 90% памяти видеокарты и отказывается стартовать, если внутри этого лимита свободно меньше 3 ГБ. На RTX 5090 32 ГБ лимит около 28 ГБ. Веса Whisper large-v3 в float16 — порядка 3 ГБ; диаризация тяжелее по памяти, и код при нехватке считает её кусками. Три большие модели в памяти одновременно не держатся.

Один глобальный замок: вторая запись ждёт, пока первая не закончит все шаги. Отдельной очереди брокера нет. Файл до 500 МБ. Таймаут инструмента 7200 с. Повтор того же файла и тех же ФИО-подсказок читает диск.

Как часто:

- Агент протокола вызывает инструмент один раз на вложение. Повторный вызов того же файла запрещён подсказкой и кэшем.
- Дальше идут лёгкие инструменты: `audio.transcript` (текст с диска, куски по 120 реплик), `audio.speakers`, `audio.propose_speakers`, `audio.bind_speakers`, `audio.transcript_docx`.
- На 500 человек это не 500 расшифровок в день. Это число совещаний, которые реально прикладывают запись. Десяток часовых записей утром встанут в одну очередь на одной карте. Равномерно по дню одна 5090 это выдерживает.

Минимум для GPU-пути: NVIDIA с CUDA, свободно не меньше 3 ГБ внутри 90% карты, на практике карта 24 ГБ уже тесная для диаризации длинного файла, 32 ГБ — запас из спецификации серверов. Диск под веса моделей — системный NVMe сервера приложения (в спецификации зеркало 2×1 ТБ). Оперативки 64 ГБ хватает: час звука в 16 кГц mono float32 — около 230 МБ, плюс загрузка модели.

## OCR, как устроено сейчас

Отдельного инструмента `ocr.*` в каталоге нет. Распознавание встроено в чтение файла.

Два провайдера, переключатель `OCR_PROVIDER`:

| | `cursor_sdk` (сейчас по умолчанию) | `lm_studio` |
|---|---|---|
| Модель | пустой `CURSOR_OCR_MODEL` значит модель агентов `grok-4.6` | `ministral-3-14b-instruct-2512` |
| Где считает | облако Cursor | LM Studio, сейчас `http://192.168.1.157:1239` |
| Страницы | по 2, до 3 пачек сразу | по 3, пачки строго по очереди |
| Таймаут пачки | 420 с | 180 с |
| Картинка | JPEG, ширина 1400 px, качество 72 | PNG, масштаб 2× |
| Видеокарта сервера приложения | не нужна | нужна, если модель крутится локально |

Страница PDF с текстовым слоем короче 40 символов считается сканом и уходит в зрение. Обычный PDF, Word и Excel читаются библиотеками, без модели.

Кто вызывает:

| Место | Когда | OCR |
|---|---|---|
| Вложения агента (`prepare_workflow_files`) | каждый новый файл при создании агента | да, по умолчанию |
| Создание регламента | PDF и прочие вложения | да |
| Зарплата и финансы | загрузка ведомости администратором | да |
| Импорт регламента-скана | отдельный конвейер | всегда LM Studio, даже если провайдер — Cursor |
| Расчёт KPI | чтение материалов | выключен |

Повторная заливка того же файла в агента снова гоняет OCR: хэш спасает только повторную запись в базу, уже после распознавания.

Как часто на 500 человек. Цифровой документ — миллисекунды CPU. Скан на 10 страниц — около пяти вызовов зрения, три из них параллельно. Если тридцать человек в один час приложат сканы, это порядка полутора сотен облачных вызовов, и каждый запрос сам поднимает до трёх процессов Node. Общего ограничителя на весь сервер нет. Видеокарта при провайдере `cursor_sdk` в этом не участвует.

Минимум для текущего OCR: ключ Cursor, Node и `desktop/sdk-agent` на сервере приложения, PyMuPDF для растеризации. Видеокарта для этого пути не требуется.

Минимум, если вернуть локальную VLM `ministral-3-14b`: квантованная модель 14B с картинками обычно просит 12–16 ГБ. На 5090 32 ГБ она помещается, пока расшифровка не заняла 90% карты. Одновременно с `asr-server` её держать нельзя: расшифровка забирает почти всю память и не отдаёт карту до конца файла.

## Каталог остальных серверных инструментов

Технология одна: HTTP backend, Postgres приложения, чужой сервис по сети. Моделей нет. Минимум — процесс API (в спецификации 16 ядер и 64 ГБ) и доступ до 1С, Exchange или IMAP.

| Инструмент | Что делает | Как часто может вызываться | Потолок в коде |
|---|---|---|---|
| `imap.list_unread`, `imap.search`, `imap.fetch_message`, `imap.fetch_attachments` | почтовый ящик сессии | по ходу агента почты, несколько раз за запуск | сеть IMAP |
| `onec.odata_catalog` | снимок метаданных, живая 1С только по `refresh` | редко, в начале незнакомой сущности | локальный JSON |
| `onec.odata_get`, `onec.sql_query` | чтение карточки или SELECT | много раз за запуск агента | SQL 45 с, только allowlist |
| `onec.erp_tasks_current`, `onec.erp_tasks_period`, `onec.erp_subordinate_tasks`, `onec.docflow_tasks` | задачи сотрудника и подчинённых | ежедневные агенты, у руководителя тяжелее | лимиты 30–200 строк |
| `onec.erp_assignments` | журнал поручений АСТ00 | проверка поручений, список и файлы | таймаут 180 с |
| `onec.download_artifact` | файл вложения 1С по GUID | когда агент открывает приложение к поручению или протоколу | таймаут 300 с, дальше файл может уйти в OCR |
| `onec.meeting_protocols`, `meetings.memo_requests` | протоколы и служебные записки на совещания | агенты РК/СД и планировщик | таймаут 180–300 с |
| `onec.incoming_correspondence` | справочник подразделений | перед регистрацией входящего | лёгкий справочник |
| `onec.meeting_protocol_write`, `onec.erp_assignments_write`, `onec.incoming_correspondence_write` | запись в 1С | после подтверждения человека, не на каждый просмотр | OData POST |
| `onec.erp_write_probe` | тестовая запись и удаление | отладка конструктора | не боевые карточки |
| `outlook.ews_availability` | занятость шефа, участников и места | каждый подбор времени совещания | таймаут 180 с, окно пн–пт 08:00–18:00 |
| `outlook.ews_create_meeting` | событие в календаре «Совещания» | один раз на служебную записку, дубль по номеру не создаётся | таймаут 180 с |
| `users.current`, `users.list`, `users.subordinates` | сессия и оргструктура | почти каждый агент, перед уведомлением | Postgres и `erp_pm` |
| `notify.send`, `chat.send_direct` | тост и личное сообщение | точечно, по шагу агента | база и доставка |
| `audio.transcript` и соседние `audio.speakers`, `audio.bind_speakers`, `audio.propose_speakers`, `audio.transcript_docx` | уже готовый текст и голоса | несколько чтений на одну расшифровку | диск и Postgres, без GPU |

На 500 человек узкое место этой группы — 1С и Exchange, не CPU Constructor. У HTTP документооборота уже есть кэш на 1800 с. Имеет смысл не опрашивать журналы чаще, чем раз в запуск агента.

Запуски самих агентов (модель `grok-4.6`, для создания регламента effort `xhigh`, для правки регламента `composer-2.5`) в этот каталог не входят, но по частоте они главные. Каждый сотрудник может запустить агента раз в день, и внутри будет много шагов. Считает облако. На сервере на каждый такой вызов поднимается процесс Node.

## Что добавлять по OCR

В репозитории нет отдельного плана новых OCR-моделей. Ниже — дыры текущего кода и минимальный следующий шаг, если сканы надо считать на своей 5090, а не в облаке.

| Инструмент | Зачем | Технология и модель | Минимум | Когда вызывать |
|---|---|---|---|---|
| Кэш OCR по хэшу файла | тот же скан не распознавать второй раз | как у аудио: sha256 → текст на диске | диск, без новой модели | перед любым вызовом зрения |
| Общая очередь зрения | тридцать одновременных сканов не плодят процессы Node | один лимит на сервер, сейчас лимит только внутри одного файла (3 пачки) | CPU сервера приложения | каждый скан |
| Один провайдер | регламент-скан сейчас всегда идёт в LM Studio, вложения — в Cursor | тот же `OCR_PROVIDER` для обоих путей | без новой модели | импорт регламента |
| Локальный OCR на 5090 | страницы не тратят квоту `grok-4.6` | уже прописанная `ministral-3-14b-instruct-2512` либо документная VLM того же класса 7–14B, квантование | 16 ГБ видеопамяти под модель, на 5090 — только когда расшифровка простаивает | скан и фото, страница без текстового слоя |
| Явный `ocr.read` | агент распознаёт файл, скачанный из 1С, отдельным шагом | тот же растеризатор PyMuPDF и выбранный провайдер | как у текущего OCR | после `onec.download_artifact`, если текстового слоя нет |
| Второй проход таблиц, печатей, рукописи | только если первый текст дырявый | та же VLM, другой промпт, не вторая резидентная модель | время той же карты или тот же API | редкие плохие страницы |

Отдельную маленькую OCR-модель «всегда в памяти» рядом с Whisper добавлять не стоит: `asr-server` и так занимает карту целиком на время записи и сам выгружает веса между шагами. Локальный OCR и расшифровка делят одну 5090 очередью, не двумя одновременно загруженными моделями.

Порядок, если сканов станет много: сначала кэш и общая очередь на текущем облачном пути, потом перенос сканов на 14B на 5090 в паузах между совещаниями. Новую модель крупнее 14B на эту карту сажать не нужно: 32 ГБ уже расписаны под Whisper large-v3 и диаризацию.
